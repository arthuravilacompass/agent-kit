1.

The controlled front door

routing-diagram Confidence 90% Complexity Medium

Description: Take rendering of the routing diagram back under the kit's control. Externalize the Mermaid source to a tracked .mmd file; pre-render it with mmdc (the kit's own mermaid-skill) into committed light and dark SVGs, verified with the existing grep data-look="handDrawn" check; embed via GitHub's <picture prefers-color-scheme> pattern. While rebuilding, strip the diagram to the one decision only it can show — the entry election (loose phrase / slash command / automatic → which owner) — deleting the 3-line prose labels crammed into nodes, and give the tech-breakdown asymmetry (the one slash path that does not route through CE) an honest distinct edge style instead of implying full connectivity.

Basis
direct: CHANGELOG (quoted in evidence dossier): "Not verifiable from here: whether GitHub's own Mermaid version honors look: handDrawn; if it does not, the diagram degrades to classic." Node labels at README.md:42 and :50 carry three rendered lines of prose each. The tech-breakdown dead-end is recorded as "an open question, not a settled design." All five ideation frames converged on pre-rendering independently.
Rationale
The user's complaint ("o diagrama não está bom") is most plausibly this documented degradation happening in production. The fix uses tooling the kit already ships, applies the kit's own epistemics (verified artifact over unverifiable delegation) to its front door, fixes dark-mode legibility, and moves 52 lines of source out of the README body — feeding idea 4.
Downsides
Committed generated assets need a regeneration step on every diagram edit (worth folding into the gate); the live-editable Mermaid preview on GitHub is lost; the clickable-nodes extension was verified false (links inside <img>-embedded SVG don't fire) — this idea ships without interactivity.
2.

Routing section 2.0

which-tool-when Confidence 85% Complexity Medium-High

Description: Rebuild "Which tool, when" around its actual job — routing. Lead with a scannable table (Situation | You say/type | What fires | Owner); open every situation with its observable discriminator, dichotomous-key style (two situations currently both say "say it loose" and route differently on an unstated utterance test — line 179 already does discriminator-first once, informally); add the missing ninth situation "I'm about to commit / I want review", giving the citation gate and /core:review-local vs /ce-code-review a trigger; and dissolve the seven-bullet "Ground rules" slab by attaching each rule to the situation where its failure actually fires (the aviation-checklist move: cautions live on the procedure step, not in a limitations chapter nobody reads). Optional add-on: a coverage check diffing INVENTORY.md's skill list against skills the section mentions (~11 shipped skills are absent today), so the index can't silently go stale.

Basis
direct: Evidence dossier: "A single table (situation → plugin → entry point) would make routing explicit and checkable"; "No situation reinforces these [ground rules]; they're discovered only when you hit the failure mode"; README:175 and :189 both open "Say it loose" and route to different skills; the citation gate has no trigger situation. external: competitor survey — no other marketplace README routes by situation.
Rationale
This section is the kit's one genuine differentiator, and it currently undermines itself: the stated boundary (syntax) differs from the actual routing (utterance), and the flagship mechanism (the citation gate) is unroutable. The redesign reinforces the differentiator instead of flattening it, and it is the direct answer to "tem blocos de texto".
Downsides
Largest rewrite in the set; the table's column vocabulary becomes doctrine (choose carefully); adding a ninth situation and per-row details pushes against the size target unless paired with idea 4.
3.

Mirror economics first

bilingual-pair Confidence 85% Complexity Small-Medium

Description: Before any restructure, settle what the pt-BR mirror owes the English file — because every idea above doubles in cost against a 247-line 1:1 mirror. GOVERNANCE.md:86 scopes the bilingual exception to "the public face" and requires only the cross-linked pair with English as source of truth — nothing mandates full-body parity. Candidate: demote README.pt-BR.md to a ~60-line front page (tagline, diagram, routing table, install line) linking into the English body for depth. Then land a check-readme-pair.sh gate verifying the mechanical invariants (byte-identical bash fences, identical Mermaid/asset references, heading order) — its first catch is already waiting: the live # or: → # ou: drift at line 94 of the pair, which violates the byte-identity rule stated in the very commit that created the mirror.

Basis
direct: Verified by direct read: README.md:94 # or: mobile · team · full vs README.pt-BR.md:94 # ou: mobile · team · full; commit 246a340's message claims "Command blocks are byte-identical between the two files." GOVERNANCE.md:86 confirmed verbatim as scoping the exception to the public face only. No tooling targets the pair today.
Rationale
The invariant broke within two days of being declared, under near-zero churn — a restructure is exactly when it breaks again. Deciding scope first, then gating it, halves the cost of every other idea in this document. Sequencing is the point: gate a policy after deciding whether the policy is full parity or front-page parity.
Downsides
Demoting the mirror reduces what pt-BR readers get natively (a judgment call about who that reader is); a sixth gate check is a standing governance change; keeping full parity instead means the gate is bigger and the tax on ideas 1–2 stays doubled.

Size-gate closure package

onboarding-path Confidence 70% Complexity Medium

Description: The only structural route back to the recorded ≤160-line / ≤14 KB target, composed of subtractions: the board-game rulebook split — README keeps the "learn to play" material (tagline, diagram, plugin table, one install path, routing table, requirements) while the "rules reference" (native install commands, AGENTS.md emission mechanics, uninstall, Advanced tables) moves to a linked docs/INSTALL.md; the externalized .mmd from idea 1 buys 52 lines; table consolidation trims duplication (postures and repo-structure tables become pointers into INVENTORY.md / GOVERNANCE.md — exact table inventory partially unverified, treat as a caveat); and check-ceiling.sh gains a twin that fails the gate when README exceeds its own recorded target, so the miss cannot silently recur.

Basis
direct: CHANGELOG.md:145 records the ≤160 / ≤14 KB target as "missed" at 247 lines / 16,749 bytes. check-ceiling.sh already implements exactly this ratchet pattern for the always-on tier (RATCHET=9776 / CEILING=16384). external: FFG's two-booklet Learn-to-Play / Rules-Reference model; inverted-pyramid README consensus.
Rationale
Every other idea adds weight; without a subtraction package the README drifts further from its own standard. The rulebook analogy supplies a principled cut line (first-session reader vs. returning reader) instead of an arbitrary trim, and the gate extension makes the target binding rather than aspirational.
Downsides
Partially reverses a week-old consolidation commit — the maintainer should own that oscillation explicitly; a second file (INSTALL.md) is a second thing to keep truthful; the "5 tables → 2" sub-claim was only directionally verified.
5.

Onboarding on doctor's spine

onboarding-path Confidence 75% Complexity Medium

Description: Restructure onboarding around what the kit already ships instead of prose promises. A compact Requirements block moves above Installation as a severity-graded matrix (hard: Claude Code / assumed-by-routing: superpowers + CE / degrades: optional plugins) with a symptom column — mirroring what doctor.sh already encodes (REQUIRED_PLUGINS=(core)). The three install paths (profile script / native commands / --tool AGENTS.md emission — today a hidden third path inside the script) become one up-front decision fork, giving the non-Claude-Code audience a visible row. The flow becomes clone → install → doctor.sh, with a small script change so doctor prints the install command for each missing external. A one-line callout surfaces doctor.sh --maintainer and the five gates — currently zero README mentions of the mode that runs what CLAUDE.md calls "the repo's CI".

Basis
direct: Evidence dossier: "No early blocker on missing superpowers/CE… the routing chain will reference skills that don't exist; doctor.sh reports as info, not fail"; "AGENTS.md emission is a third path (--tool flag) hiding inside the script"; --maintainer confirmed at doctor.sh:3,18–23 with zero README mentions of "maintainer".
Rationale
The README's current ordering manufactures the kit's worst onboarding failure: a routing map referencing tools that don't resolve, with no symptom table to debug it. A kit whose thesis is "deterministic verifiers over prose promises" onboarding via prose promises is a brand contradiction — making doctor the spine is both simplification and identity statement.
Downsides
Requires a (small) doctor.sh change, so it's not a pure doc edit; moving Requirements up front trades a little "pitch first" energy for correctness of sequence.

Honest badges + generated plugin table

visual-richness Confidence 65% Complexity Small-Medium

Description: The README has zero badges against a 2–4 norm — but stock shields would violate the kit's own epistemics, since no CI exists to back a status badge ("this gate is the repo's CI" = a local script). The honest versions: (a) a minimal GitHub Actions workflow that runs the existing five-part gate on push, backing a real gate-status badge; and/or (b) per-plugin version badges generated from plugin.json — mechanically truthful because the repo's commit rule bumps version and CHANGELOG in the same commit as the behavior change — palette-matched to the diagram (#fefdfa field) rather than default shields green. Same move applied to content: generate the "What's included" plugin table from plugin.json, the way generate_inventory.py already generates INVENTORY.md. If the Actions cost is declined, record "no badges, on principle" as a decision instead of a default.

Basis
direct: "Zero shield.io, GitHub Actions badge, or custom badges" (evidence dossier); CLAUDE.md: "There's no separate build/test command — this gate is the repo's CI"; commit rule: "version and changelog land together with the change, never as a follow-up"; generate_inventory.py as live precedent for generated markdown. external: shields.io guidance, 2–4 badge norm.
Rationale
A green gate badge on a repo about verification is the thesis made visible — visual richness that inherits the kit's discipline instead of decorating over it. The generated table kills a silent-drift surface (hand-maintained versions) at zero marginal cost per release.
Downsides
The backed-badge variant is infrastructure work (a new Actions workflow), not a README edit — a real scope call; generated README fragments add a build step to doc edits; unbacked version badges are the only zero-infra option and cover less.
